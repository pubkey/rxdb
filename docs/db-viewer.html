Database Viewer

In a local-first app the data lives on the user's device and not on a server where you can just log in and look at it. With the dbviewer plugin you get a devtool over a running RxDB database, either locally in your app or remotely connected to your user's device. You can browse every RxCollection, run queries, edit documents and watch replication.

Beta Feature(available since version 17.7.0)
This feature is in beta and may have breaking changes without a major RxDB version release.

Quick Start​

Mount the viewer into any element of your app:

The Usage section shows how to load it lazily and how to use it with Angular, React, Vue and Svelte.

There are three ways to open the viewer:

  • Mount it into your app with mountRxDBViewer().
  • Connect from another browser with connectRxDBViewer(). The viewer page pairs with your app over WebRTC, which is useful when the app runs on a phone.
  • Open a JSON dump that was created with the json-dump plugin. This works when you cannot reach the device at all.

All three show the same UI.

What the Viewer Shows​

Browse and Query​

  • Data grid and JSON view: Lists the documents of a collection with limit (default: 20) and skip inputs and a sort dropdown. The sort is part of the query, so clicking a column header sorts the whole collection and not only the current page. The grid only renders the visible rows, so a limit of 10k does not slow down the page. Live mode is on by default and updates the result whenever a matching document changes.
  • Mango query bar: Runs MongoDB-style (Mango) selectors with a history and favorites. You do not have to write strict JSON, { done: false } with unquoted keys and single quotes works too. When the selector has a syntax error, the viewer shows the character position and keeps the previous results visible.
  • Document drawer: Shows the fields, the internals (_rev, _meta.lwt) and the attachments of a document, with inline previews for images. A JSON tab lets you edit the whole document as raw JSON. The primary key is protected against accidental changes.
  • System collections: The internal store, the local documents and the collections behind RxState are listed in a SYSTEM group. You can browse, query and export them, but editing is disabled.

Analyze​

  • Schema panel: Samples documents and shows for each field which types it has and in how many documents it is present. Documents that do not match the declared schema are listed as violations.
  • Explain button: Shows which index the current query uses and the execution plan from the query planner. It also points out problems like a missing compound index or a $regex that has to scan all documents.
  • Live activity map: Draws your app, its collections and the remote endpoints as a map, and every write, query and replication event moves along it. Each collection shows a 60 second sparkline and the number of cached RxQuery instances. The map only contains names, counts and rates, never document contents, so you can share your screen while it is open.
  • Changes and replication feeds: The Changes feed lists the writes of a collection like the network tab of the browser devtools, with a diff per change. You can download it as a JSON array. The Replication panel shows the pull and push state of each replication and the documents that are replicated.

Maintain​

  • Storage panel: Shows the storage engine and, per collection, the number of documents, tombstones and attachment bytes.
  • Cleanup tool: Shows per collection how many deleted documents could be purged and how much of the stored data that is. When the cleanup plugin is added, you can run the cleanup from here.
  • Export tool: Downloads the database as one JSON file. You can pick the collections and set a selector per collection, so only the matching documents end up in the file.

Usage​

1

Mount the Viewer​

Call remove() when you no longer need the viewer.

2

Load It Lazily​

Importing mountRxDBViewer adds about 13 kB (gzip) to your bundle, and including connectRxDBViewer with its WebRTC connection adds about 48 kB (gzip). Load it with a dynamic import() when the viewer is opened, so it is not part of the initial page load.

If you prefer a method on the database, add the plugin and call launchDbViewer():

Usage with Frameworks​

Mount the viewer when the component is rendered and call remove() when it is destroyed. The viewer does not close itself. With showCloseButton set, a click on the close icon emits on close$ and your app decides what to do, for example hide the panel.

How It Works​

The plugin itself contains no UI code. mountRxDBViewer() creates an iframe that loads the viewer page from rxdb.info/db-viewer/index.html and then serves the database to that iframe over postMessage. The page is one self-contained HTML file.

So the UI is not part of your bundle, only the small bridge is. The page inside the iframe never gets access to the database object. Queries, the query plan analysis and the event streams run in your application window, and the page only receives the results.

Options​

Remote Pairing over WebRTC​

When the app runs on a device you cannot attach a debugger to, for example a phone in field testing, call connectRxDBViewer() in the app and open the returned url in any browser:

The url contains the room id and the signaling server in its hash, so the page connects as soon as it is opened. When you open the page without a hash, it shows a form where you enter the values by hand. A room id must have at least 6 characters, otherwise DVW3 is thrown.

All features work over WebRTC because it uses the same bridge protocol as the iframe mount. The signaling server only brokers the connection, the data flows directly between your browser and the device. You can run your own signaling server with startSignalingServerSimplePeer() as described in the WebRTC replication docs.

The Angular example puts this behind a debug flag. When you open the app with ?debug=dbviewer-webrtc, it connects the database and logs the pairing url to the console.

Dump Mode​

When you cannot reach the device at all, for example when a user sends you their data with a bug report, work with an export. On the device, call await myDatabase.exportJSON() from the json-dump plugin, save the result and open it in the viewer:

The grid, the queries, the Schema panel and the storage counts work the same as with a live database. Editing, Live mode, the activity map and the feeds need a running database, so they are disabled and show a "not available on a dump" hint. You can also open a dump file at runtime from the Export/Import tool.

Self-Hosting the Viewer Page​

When your app has to run offline or your Content Security Policy does not allow pages from other origins, serve the viewer page from your own origin. Because the page is one self-contained HTML file, self-hosting is just a file copy:

  1. Get the file. Download it once from rxdb.info/db-viewer/index.html, or build it from the RxDB repository with npm run build:dbviewer, which writes it to docs-src/static/db-viewer/index.html.
  2. Serve it as a static asset of your app, for example as public/dbviewer.html. It has to be served over http(s). A file:// url does not work because postMessage needs an origin.
  3. Set the viewerUrl option to the url of your copy:

The Angular example does this in its postinstall script. It copies the built page to src/assets/dbviewer.html and mounts the viewer with viewerUrl: 'assets/dbviewer.html'.

The page and the plugin talk over a versioned protocol, so update your self-hosted copy whenever you update RxDB.

Limitations​

  • The viewer renders into the DOM. It runs in browsers, Electron renderers and webviews, but not in plain Node.js.
  • With the default viewerUrl, the first load needs network access to rxdb.info. For offline apps, host the page yourself.
  • The reads counter of the activity map is derived from the query cache counters. Reads that bypass the cache are not counted.

FAQ​

Can I inspect an RxDB database in production?

Yes. The viewer is a normal plugin and is only shown where you mount it, for example behind a feature flag or an admin route. Keep in mind that everyone who can open the viewer can read and edit all data of the local RxDatabase.

Does the RxDB database viewer increase my bundle size?

Only a little. The UI is a hosted page that loads inside an iframe, so only the mount function and the bridge are part of your bundle, which is about 13 kB (gzip). With a dynamic import() the plugin is not loaded at all until you open the viewer.

Can the viewer page read my database when I do not open it?

No. The page only receives data over the bridge that mountRxDBViewer() or connectRxDBViewer() creates.

Does the database viewer work with any RxStorage?

Yes. The viewer reads the data through the normal query API, so it works with every RxStorage. To count tombstones, the Storage panel also reads from the storage instance, which works with all official storages.

Does the viewer show replications that start after it was mounted?

Yes. The Replication panel polls for replication states created with replicateRxCollection() or one of the replication plugins in the same JavaScript context.

Does the RxDB database viewer show encrypted fields in plain text?

Yes. The viewer reads documents through the RxDB query API and not from the raw storage, so fields that are stored with the encryption plugin show up decrypted. The same goes for key compression: you see the normal field names and not the compressed keys. Keep this in mind before you share your screen or open the viewer on a production device.

Can I use the database viewer with React Native or Capacitor?

Yes. In a Capacitor app the code runs in a webview, so you can mount the viewer directly. React Native has no DOM, so mountRxDBViewer() does not work there. Instead, call connectRxDBViewer() in the app and open the pairing url in a browser on your machine. This needs a WebRTC implementation in the React Native JavaScript context, for example from react-native-webrtc. When that is not possible, export the data and use the dump mode.
