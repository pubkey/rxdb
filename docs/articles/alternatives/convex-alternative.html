RxDB as a Convex Alternative or Offline Layer for Convex Apps

Convex is a reactive backend for TypeScript apps. You write queries and mutations as TypeScript functions that run on the server, and every client query is a live subscription that updates when the underlying data changes. The developer experience is the main reason teams pick it, and the numbers show it: the convex npm package was downloaded 6,188,547 times between September 27 and October 26, 2026 (npm), and the company raised a $57M Series B in August 2026.

If you are looking for a Convex alternative, the reason is usually offline support, vendor lock-in, or pricing. RxDB is a local-first, NoSQL database for JavaScript that stores data on the device and syncs with any backend through its Sync Engine. This page explains how Convex works, where it falls short for offline-first apps, and how you can either replace it with RxDB or keep Convex and add RxDB as its offline layer.

A Short History of Convex​

Convex was founded in 2021 by former Dropbox infrastructure engineers, including CEO Jamie Turner and CTO James Cowling (about us). Several team members worked on the Dropbox desktop sync engine. The product combines a transactional document database, server functions, file storage, scheduling, and auth in one hosted platform.

  • March 2024 - The Convex backend is published as source-available code under the FSL-1.1-Apache-2.0 license, so it can be self-hosted.

What is RxDB?​

RxDB (Reactive Database) is a local-first, NoSQL database for JavaScript applications. It runs in the browser, Node.js, Electron, React Native, Capacitor, Deno, and Bun. Documents are validated against a JSON schema, queries use MongoDB-style (Mango) queries, and every query is an observable that emits when the result changes.

Data lives in a local storage of your choice, such as IndexedDB, OPFS, or SQLite. The replication protocol syncs that data with any backend, including CouchDB, GraphQL, Firestore, Supabase, a custom HTTP API, or Convex itself.

Where Convex Falls Short​

1. No Offline Support​

Convex is online-first. The client keeps an in-memory cache of query results, not a persistent local database. Convex states it on its own sync page: "Convex doesn't currently provide a full offline sync mechanism, but some customers have used tools like Replicache." When the device is offline for longer than a network blip, the app cannot query data it has not loaded, and it cannot store writes across a reload. With RxDB, the full dataset of a collection lives on the device and every query runs locally, which makes it an offline database.

2. Optimistic Updates Are Temporary​

Convex optimistic updates are "temporary, local changes to your query results" that are "rolled back when a mutation completes" (docs). You write a separate update function for each mutation that should feel instant. In RxDB, every write goes to the local database first, so the UI updates at once without extra code, and the write survives a reload. See optimistic UI.

3. Lock-In to the Convex Function Model​

Your backend code is written against ctx.db and the Convex function types. Moving off Convex means rewriting queries, mutations, and authorization. The backend is source-available under FSL-1.1, which converts to Apache 2.0 only two years after each release (license). RxDB is Apache 2.0, and its replication works with the backend you already run.

4. Imperative Queries​

Convex has no query language. You write queries as TypeScript functions with index ranges, and joins are loops in your code. RxDB has declarative Mango queries that run on the device, with indexes defined in the schema.

5. Usage-Based Pricing on Every Read​

On Convex, every query run is a billed function call. The Professional plan costs $25 per developer per month and includes 25M function calls. The Starter plan charges $2.20 per million function calls beyond the free limit. A realtime app that re-runs subscriptions for many clients pays for server work on every change. With RxDB, reads hit the local database and cost nothing on the server.

As of October 27, 2026, the Convex backend repository has 12,760 GitHub stars while RxDB has 23,416.

Using RxDB as an Offline Layer for Convex​

You do not have to leave Convex to get offline support. RxDB can hold the data on the device while Convex stays the server and source of truth. The UI only reads and writes RxDB, and the RxDB replication syncs with Convex in the background:

  • Pull is a Convex query that returns all documents changed after a checkpoint.
  • Push is a Convex mutation that writes the changed documents and returns conflicts.
  • Live updates come from a Convex subscription. When it fires, RxDB pulls again.

Convex mutations run as serializable transactions, so the conflict check in the push mutation is safe without extra locking.

The Convex Side​

Each synced table gets a client-generated string id (RxDB creates documents before the server knows them, so it cannot use the Convex _id), a deleted flag so that deletions replicate, and a serverSeq number that orders the changes.

serverSeq comes from a counter document that every push increments. Do not use Date.now() for it. A mutation that starts earlier but commits later would write a smaller timestamp than a checkpoint that a client already pulled, and that client would never see the change. Because Convex retries transactions that conflict on the counter, the counter follows the real commit order.

Things to Keep in Mind​

  • Every write path has to bump the counter. A Convex mutation that changes todos outside of push has to increment serverSeq too, or clients never pull that change.
  • One counter means one hot document. All pushes conflict on the counter, which limits write throughput. When documents belong to a user or a tenant, use one counter per user and filter the pull query with ctx.auth, so that each user only receives their own documents.
  • Stay below the Convex limits. A Convex function can read 16 MiB and write 16,000 documents (limits), so keep the pull and push batch sizes small.
  • Deleted documents stay as tombstones. Clean them up with a scheduled function after all clients had time to pull them.
  • Pulls and pushes are billed function calls, but local reads in the app are not.

When Convex Still Makes Sense​

  • Online-only apps with server logic: When your app always has a connection and you want database, server functions, auth, file storage, and scheduling in one product with end-to-end types, Convex removes a lot of backend work.
  • Strong consistency across users: Convex runs serializable ACID transactions on the server. RxDB syncs devices eventually and resolves conflicts per document.
  • Native Swift and Kotlin clients: Convex ships first-party clients for iOS and Android. RxDB is JavaScript only.
  • You want offline support without leaving Convex: Add RxDB as the offline layer as shown above, and keep Convex as the backend.

FAQ​

Does Convex work offline?

No. Convex handles short network interruptions, but it "doesn't currently provide a full offline sync mechanism" according to its own sync page. The client caches query results in memory, and optimistic updates are rolled back after the mutation completes. RxDB stores the data on the device, so queries and writes work without a connection.

Can I use RxDB together with Convex?

Yes. Use a Convex query as the pull handler, a Convex mutation as the push handler, and a Convex subscription to trigger new pulls. The RxDB replication then keeps the local database in sync with Convex, and the app keeps working offline.

Is Convex open source?

No, not fully. The convex client package is Apache 2.0. The backend is source-available under FSL-1.1-Apache-2.0, which allows self-hosting but restricts competing uses until each release converts to Apache 2.0 after two years. The RxDB core is Apache 2.0.

What is the best Convex alternative for a local-first app?

For a local-first JavaScript app, use a client-side database with replication, such as RxDB, and sync it with the backend you already run. If you want a hosted Postgres sync service instead, compare the PowerSync alternative page.
