RxDB as a Turso and libSQL WASM Alternative for Browser Apps

Turso is the company behind libSQL, an open source fork of SQLite, and Turso Database, a rewrite of SQLite in Rust. Both run on servers, at the edge, and in the browser through WebAssembly, and Turso Cloud adds hosted databases and sync. The team has shipped a lot of database engineering in a short time, and its Rust rewrite has 25,068 GitHub stars as of October 27, 2026. On October 2, 2026, Supabase announced that it is acquiring Turso.

If you want a Turso alternative or a libSQL WASM alternative for a browser app, the question is usually not "which SQL engine is better". It is how to get local data that persists, works in every tab, and stays in sync with a server. RxDB is a local-first, NoSQL database for JavaScript with a pluggable storage layer, reactive queries, and a Sync Engine. This page explains what Turso and libSQL offer in the browser today, where they fall short for local-first web apps, and how RxDB covers the same use cases.

A Short History of Turso and libSQL​

Glauber Costa and Pekka Enberg forked SQLite as libSQL in 2022 because SQLite does not accept outside contributions. libSQL added features such as a server mode, replication, and vector search, and their company built a hosted edge database on top of it. In December 2024 they announced Limbo, a full rewrite of SQLite in Rust, which later became Turso Database and the main focus of the team.

A Brief Timeline​

  • 2022 - libSQL is forked from SQLite (coverage). The company, then called ChiselStrike, later renames itself to Turso.
  • December 10, 2024 - Limbo is announced as a rewrite of SQLite in Rust.
  • January 21, 2025 - Turso goes all-in on the rewrite. The new multitenant server is announced as closed source, edge replicas are discontinued for new users, and "everything that runs on the client will remain strictly open source" (roadmap post).
  • March 31, 2025 - Offline sync public beta for TypeScript and Rust. The browser is "planned for the future".
  • July 1, 2025 - First alpha of Turso Database.
  • October 8, 2025 - Turso in the browser via the @tursodatabase/database-wasm package, and the beta of Turso Sync.
  • October 2, 2026 - Supabase announces the acquisition of Turso. Both posts say Turso Cloud keeps running and Turso Database stays open source.
  • October 12, 2026 - Turso Database 0.8.3 is the latest release on npm.

Turso and libSQL in the Browser Today​

There are two ways to run Turso technology in a browser.

Turso Database via @tursodatabase/database-wasm (MIT, version 0.8.3 as of October 2026). Queries run on the main thread, and the library starts a Web Worker for all file operations through the synchronous OPFS (Origin Private File System) API. A minimal example from the Turso announcement:

libSQL via @libsql/client-wasm (version 0.18.0). This client wraps @libsql/libsql-wasm-experimental, which describes itself as "libSQL Wasm packaged as an ES module, forked from SQLite Wasm". It is based on SQLite 3.44.0 and has not been released since October 31, 2024. Calling sync() in this client throws "sync not supported in wasm mode", and encryption is not supported either.

For server-side apps, Turso also offers embedded replicas and Turso Sync, which keep a local database file in sync with Turso Cloud. Those need a file system, so they target Node.js, mobile, and desktop, not the browser.

What is RxDB?​

RxDB (Reactive Database) is a local-first, NoSQL database for JavaScript applications. It runs in the browser, Node.js, Electron, React Native, Capacitor, Deno, and Bun. Documents are validated against a JSON schema, queries use MongoDB-style (Mango) syntax, and every query can be observed as an RxJS observable.

RxDB does not ship its own storage engine. Instead, it runs on top of a storage of your choice: IndexedDB, OPFS, SQLite, memory, or localStorage. Switching storages is a configuration change, not a rewrite.

Where Turso and libSQL Fall Short in the Browser​

1. COOP and COEP Headers Are Required​

Turso Database shares memory between the main thread and its worker through SharedArrayBuffer. The Turso announcement says: "This requires additional COEP / COOP headers to be set for document resource." The bundled code throws when SharedArrayBuffer is not available. These headers break embedded third-party iframes, some OAuth popups, and ads, and many static hosts do not let you set them at all. RxDB storages work without special headers.

2. One Tab Only​

The OPFS access handle locks the database file to one worker. In Turso's own words, this "will prevent usage of same database from different browser tab." Users open apps in several tabs, so you have to build tab coordination yourself. RxDB has multi-tab support built in: all tabs see the same data, changes in one tab show up in the others, and replication runs only in one tab through leader election.

3. Large WASM Download​

The browser has to download and compile the database engine before the first query. We measured the turso.wasm32-wasi.wasm file of @tursodatabase/database-wasm 0.8.3 at 11.6 MB raw and about 3.9 MB gzipped. The CDN bundle, which inlines the WASM as base64, is 16.0 MB. For comparison, the official SQLite WASM binary is about 938.9 kB uncompressed. In our browser storage benchmark, WASM SQLite needed 504 ms until it could store the first document while IndexedDB needed 46 ms. A binary that is more than ten times larger will not start faster.

4. No Sync in the Browser Docs​

Turso Sync has a browser package (@tursodatabase/sync-wasm), but the official SDK reference lists only Node.js for sync, and the libSQL WASM client does not sync at all. Where sync works, the remote is Turso Cloud and conflicts are resolved by "last push wins". There is no custom conflict handler. The RxDB replication protocol runs in the browser, works with any backend, and lets you write a conflict handler per collection.

5. Pre-1.0 Engine With Compatibility Gaps​

The Turso Database README says it "runs in production today at multiple organizations" but has not reached 1.0 and recommends keeping backups. Its compatibility list names gaps such as no FTS3/4/5, no WITH RECURSIVE, and WAL as the only journal mode. libSQL is battle-tested, but Turso writes that "new features are being developed in Turso", and the browser build of libSQL is still marked experimental.

6. Open Questions After the Acquisition​

Supabase writes that "For existing users, nothing changes" and that Turso continues its SQLite work. Neither the Supabase post nor the Turso post mentions libSQL, pricing, or the browser and offline sync roadmap. Notice that this is the third hosted sync product in 2026 whose future changed through an acquisition, after Electric Cloud and Instant Cloud. RxDB is independent and funded by 👑 RxDB Premium plugins, and its replication runs against your own backend.

When Turso or libSQL Still Makes Sense​

  • Server-side SQLite: For a backend that needs one SQLite database per tenant or per AI agent, Turso Cloud and embedded replicas are built for exactly that. This is a server use case, not a browser one.
  • You need SQL in the browser: If your app runs complex SQL queries over local data and you control the response headers, Turso Database in the browser gives you a SQLite-compatible engine with an async API. Also compare it with SQLite-Wasm and PGlite in RxDB vs SQLite WASM vs PGlite.
  • You want open source engine work: Turso Database is MIT licensed, and the team publishes its engine work in the open.

FAQ​

Can Turso run in the browser?

Yes. Turso Database runs in the browser through the @tursodatabase/database-wasm package, which stores data in OPFS through a Web Worker. It requires COOP and COEP headers, and the same database cannot be used from several browser tabs. RxDB runs in the browser without special headers and supports multiple tabs out of the box.

Does libSQL WASM support offline sync?

No. The @libsql/client-wasm client throws "sync not supported in wasm mode" when you call sync(). Turso's sync features target environments with a file system. The RxDB Sync Engine runs in the browser and syncs with any backend.

What happens to Turso after the Supabase acquisition?

Supabase and Turso both state that Turso Cloud keeps running and that Turso Database stays open source. Neither announcement mentions libSQL, pricing, or the browser roadmap. If you want a local database whose sync does not depend on a hosted service, RxDB replicates with your own backend.

Is RxDB a SQL database?

No. RxDB is a NoSQL document database with MongoDB-style (Mango) queries. It can use SQLite as its storage engine through the SQLite RxStorage, but the query language works on JSON documents and has no joins.
