RxDB as an InstantDB Alternative After the Instant Cloud Shutdown

InstantDB made realtime, collaborative apps easy to start: a client SDK with optimistic updates, a Datalog-style query language, and a hosted sync service that just worked. Now that Instant Cloud is closing, many teams are looking for an InstantDB alternative and have a deadline to meet.

Instant Cloud is shutting down

In August 2026 the Instant team joined OpenAI. New Instant Cloud signups are closed, all Instant Cloud apps shut down on August 31, 2027, and backups stay available until August 31, 2028 (announcement).

RxDB (Reactive Database) is a local-first, NoSQL database for JavaScript applications that stores data on the device and replicates with any backend you run. This page explains what the Instant Cloud shutdown means for existing apps, where InstantDB falls short as a local database, and how to move an InstantDB app to RxDB with your own Sync Engine backend.

A Short History of InstantDB​

InstantDB launched in 2023 out of Y Combinator. The product centers on a sync server written in Clojure that talks to Postgres and exposes a Datalog-style query language (InstaQL) to JavaScript clients. Clients write through optimistic updates, the server stores the canonical state, and changes are streamed back to every connected device. The design works well for prototypes and collaborative tools, and the SDK handles subscriptions and rollbacks automatically.

A Brief Timeline​

  • 2023 - InstantDB launches as a Y Combinator company with a hosted sync service.
  • 2024 - The full stack, including the Clojure server, is published under the Apache 2.0 license on GitHub.
  • July 31, 2026 - Subscriptions started after this date are fully refunded.
  • August 2026 - The Instant team joins OpenAI. New signups for Instant Cloud are closed (announcement).
  • August 31, 2027 - All Instant Cloud apps shut down.
  • August 31, 2028 - Instant Cloud backups are no longer available.

What the Instant Cloud Shutdown Means for Your App​

The announcement is clear: "Existing users should migrate off of Instant Cloud within the next 12 months." There are two paths. You can self-host Instant, or you can move to a different stack.

Instant stays open source, and the team published a migration guide to self-hosting. Following it, you set up your own Instant server, rehearse with a test backup, switch Instant Cloud to read-only, restore a final backup, and deploy a client release with the new app ID and URLs. The guide states that "Migrating without data loss will require some downtime." During the cutover, writes are blocked, and users may have to sign in again.

Self-hosting keeps your app code unchanged. But you take over the operation of a Clojure sync server and its Postgres database, and the project that you depend on no longer has its original team working on it full-time. This is the trade-off to evaluate before you choose a path.

If you have to touch the backend anyway, the migration is also the moment to move to a stack where the sync server is a small part of the backend you already run, instead of a separate service that you have to keep alive.

What is RxDB?​

RxDB (Reactive Database) is a local-first, NoSQL database for JavaScript applications. It runs in the browser, Node.js, Electron, React Native, Capacitor, Deno, and Bun. It is built around three ideas:

  • Local-first storage: every read and write hits a local engine first. The app keeps working when the network is gone. See offline-first.
  • Reactive queries: any RxQuery returns an observable that emits again when matching data changes, locally or from a remote push. See reactivity.
  • Pluggable replication: the Sync Engine talks to any HTTP endpoint, GraphQL server, CouchDB, Firestore, Supabase, or peer over WebRTC. The protocol is documented, so you can implement it on any backend with HTTP replication.

Storage is also pluggable. The same collection can run on IndexedDB, OPFS, SQLite, in-memory, or localStorage without changing application code.

Where InstantDB Falls Short​

The shutdown is the urgent reason to move, but some limits of InstantDB also apply to a self-hosted Instant server.

1. The Backend Is a Fixed Service​

Instant clients only talk to an Instant server. Your data model, permissions, and sync all live inside that Clojure service and its Postgres schema. When you self-host, you operate the full Instant backend next to your own services. With RxDB, the sync endpoints are a few routes in the backend you already have, written in the language you already use.

2. Datalog Has a Learning Curve​

InstantDB queries use a Datalog-style syntax. The model is expressive once it clicks, but new contributors have to learn it before they can ship a feature. RxDB uses MongoDB-style (Mango) queries that are familiar to anyone who has used MongoDB or PouchDB.

3. The Local Layer Is a Cache​

InstantDB stores the results of subscribed queries on the client so the UI stays responsive during network drops. It is not a full local database. You cannot run arbitrary queries over data that was never subscribed. RxDB stores every document of every replicated collection on the device and lets you query any field at any time, which makes it an offline database and not just a cache.

4. Few Storage Options​

The InstantDB client picks its own persistence layer. RxDB exposes an RxStorage interface with storages for IndexedDB, OPFS, SQLite, memory, localStorage, Dexie, and more. You can switch storages per platform. Switching storages is a configuration change, not a rewrite.

5. Limited Conflict Resolution Knobs​

InstantDB resolves write conflicts internally. You get optimistic updates and rollback, but the resolution policy is mostly fixed. RxDB lets you write a custom conflict handler per collection, or use CRDTs when you need automatic merging.

As of October 27, 2026, InstantDB has about 10,600 GitHub stars while RxDB has 23,416.

Why Teams Pick RxDB Instead​

Bring Your Own Backend​

RxDB does not ship with a mandatory cloud. A collection connects to whatever you already run:

  • A REST API over HTTP replication.
  • A GraphQL endpoint with subscriptions.
  • CouchDB, Firestore, or Supabase with the official replication plugins.
  • WebRTC peers for direct device-to-device sync.

The sync protocol is a pull plus push plus event stream contract. Anything that can implement those three calls can be an RxDB backend. No vendor can shut it down for you.

Open Source and Independent​

The RxDB core is Apache 2.0. The project has been maintained since 2016 and is funded by 👑 RxDB Premium plugins, not by venture capital that needs an exit.

Observable Queries Out of the Box​

Every query is an RxJS observable. UI frameworks subscribe once and re-render when data changes. See reactivity and optimistic UI.

Multi-Tab​

The same code runs in every browser tab. The multi-tab support makes sure two tabs see the same state, and replication runs only once through leader election.

Moving an InstantDB App to RxDB​

Instant Cloud offers on-demand backups, and the data model of an InstantDB app is a set of namespaces with attributes and links. In the following, these steps move such an app to RxDB:

  1. Map each namespace to an RxDB collection and write a JSON schema for it. Links between namespaces become id fields or arrays of ids, which RxDB can resolve with population.
  2. Load your data into your own backend database. Use the Instant admin SDK or a backup to export the entities, and write them to the database that will be the source of truth, for example Postgres or MongoDB. Add an updatedAt field and keep deleted entities as tombstones with a _deleted flag.
  3. Add pull, push, and stream endpoints to your backend as described in the HTTP replication docs. Move your Instant permission rules into these endpoints, so each user only pulls and pushes the documents they are allowed to see.
  4. Replace useQuery and transact calls with RxDB queries and writes as shown above.
  5. Ship the new client release before August 31, 2027. Clients that open the new version start a fresh initial replication from your backend.

Because the RxDB client keeps working offline, users who open the app during the cutover can keep writing locally. Their changes are pushed as soon as the new backend is reachable.

When InstantDB Still Makes Sense​

If your app is small, your team is happy with InstaQL, and you are fine operating a Clojure service and its Postgres database, self-hosting Instant is the path with the fewest code changes. The self-hosting guide is well written, and the code is Apache 2.0, so nobody can take it away from you.

FAQ​

When does Instant Cloud shut down?

On August 31, 2027, all Instant Cloud apps shut down. New signups are already closed, and backups stay available until August 31, 2028. Moving to RxDB with your own backend removes the dependency on any hosted sync service.

Is InstantDB self-hostable?

Yes. Instant is open source under Apache 2.0 and publishes a self-hosting guide. Migrating from Instant Cloud to a self-hosted server requires some downtime, and you have to operate the Clojure server and its Postgres database yourself. With the RxDB Sync Engine, the sync endpoints live inside the backend you already run.

What is the best InstantDB alternative for a local-first app?

That depends on your backend. If you want a full local database that syncs with a backend you own, RxDB fits because it replicates with any HTTP, GraphQL, CouchDB, Firestore, or Supabase backend. If you want to keep Postgres and a hosted sync service, look at the PowerSync comparison.

Does RxDB use Datalog?

No. RxDB queries use a JSON Mango syntax similar to MongoDB. The format is documented in RxQuery and supports selectors, sorting, indexes, and limits without a separate query language.

How does RxDB handle optimistic updates?

Every write goes to the local storage first and resolves immediately. Observable queries emit the new state, so the UI updates without waiting for the server. The Sync Engine pushes the change in the background, and conflicts go through the collection's conflict handler.
